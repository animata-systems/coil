# 07. Streams

| | |
|---|---|
| **Статус** | Смешанный (см. § 7.1a) |
| **Назначение** | Потоки, события, сигналы |

---

## 7.1. Зачем потоки нужны языку

Простая модель «запусти и дождись финала» недостаточна для агентной ОС. Реальные сценарии требуют:

- запустить размышление LLM;
- параллельно написать тех. отделу;
- открыть внешний диалог с клиентом;
- по мере поступления новых данных отправлять уточнения в уже идущее размышление.

Это приводит к модели **открытых потоков / сессий**.

---

## 7.1a. Статусная карта

| Область | Статус |
|---|---|
| Пространство имён `~name` зарезервировано за stream references | Stable |
| Потоки как отдельный класс сущностей, отличный от `?promise` и `$value` | Stable |
| Ownership: поток принадлежит экземпляру-создателю | Stable |
| Ordering: FIFO в каждом направлении | Stable |
| Buffering: обязательная буферизация вне активного `ЖДИ`; лимит — host-defined; overflow — ошибка исполнения | Stable |
| `СИГНАЛ ~name`: асинхронный, кооперативный, в буфер | Stable |
| Close: поток закрывается с разрешением `?name`; `СИГНАЛ` после close — ошибка исполнения | Stable |
| `~name` creation: язык определяет разрешённые операторы; хост-среда решает, будет ли поток реально создан | Stable |
| Событийная форма `ЖДИ ... ИЗ ~...` | Experimental |
| Shape event object | Experimental |
| Broadcast, compete, cross-instance routing | Deferred |
| Rich event shape | Deferred |
| Cancellation / interruption model | Deferred |

---

## 7.2. Поток и обещание

В тех потоковых сценариях, где оператор открывает живой поток, используются две проекции:

| Сущность | Ссылка | Назначение |
|---|---|---|
| Обещание финального результата | `?name` | Терминальная проекция |
| Открытый поток | `~name` | Живая двусторонняя сессия |

Иллюстративные примеры возможной проекции:

| Оператор | Обещание | Поток |
|---|---|---|
| `ДУМАЙ решение` | `?решение` | `~решение` |
| `НАПИШИ ответ` | `?ответ` | `~ответ` |
| `ВЫПОЛНИ диалог` | `?диалог` | `~диалог` |

> Примечание: пространство имён `~name` и сама идея stream-проекции stable, но конкретная матрица `оператор -> гарантированное создание потока` остаётся experimental.

---

## 7.3. События и сигналы

Поток обладает двумя направлениями взаимодействия:

| Направление | Механизм | Описание |
|---|---|---|
| Из потока | **Событие** | Данные, поступающие из открытого потока |
| В поток | **Сигнал** | Данные, отправляемые оператором `СИГНАЛ` |

> Примечание: термин «interrupt» сознательно не используется. Модель доставки — кооперативная: сигнал помещается в буфер потока, получатель принимает его в своей точке исполнения.

---

## 7.4. `ЖДИ` для событий

> Статус: experimental.

Кроме ожидания обещаний, `ЖДИ` должен уметь ждать **следующее событие** из потоков.

### Форма (experimental)

```coil
ЖДИ event
ИЗ ~решение, ~ответ, ~диалог
НЕ БОЛЕЕ 10м
КОНЕЦ
```

### Семантика

- `$event` — объект события, по которому можно ветвиться.
- Минимально ожидаемые поля события: источник, тип, данные, время.

> Примечание: точный shape события не зафиксирован.

---

## 7.5. `СИГНАЛ`

```coil
СИГНАЛ ~решение
<<
Клиент сообщил новый номер договора: $contract_id
>>
КОНЕЦ
```

### Семантика

- `СИГНАЛ` не создаёт новый поток. Он отправляет данные в уже существующий поток `~name`.
- Доставка асинхронная: сигнал помещается в буфер потока. Получатель принимает его в согласованной точке исполнения.
- `СИГНАЛ` после закрытия потока считается ошибкой исполнения.

---

## 7.6. `ВЫПОЛНИ`

`ВЫПОЛНИ` — единый оператор работы с инструментами. В потоковых сценариях он может иметь promise-проекцию `?name` и stream-проекцию `~name`, но точная гарантия создания потока и его жизненный цикл пока остаются experimental. Для one-shot инструментов поток может закрываться сразу; для интерактивных сессий — оставаться открытым.

```coil
ВЫПОЛНИ диалог
ИСПОЛЬЗУЯ !открыть_чат_с_клиентом
- topic: "уточнение номера договора и времени сбоя"
КОНЕЦ
```

## 7.7. Ownership и lifecycle потока

### Ownership

Поток `~name` принадлежит экземпляру протокола, создавшему его. События доставляются только этому экземпляру. Cross-instance routing — deferred.

### Ordering

Среда исполнения обязана гарантировать FIFO-порядок в каждом направлении:
- события из потока поступают в порядке их возникновения;
- сигналы в поток доставляются в порядке их отправки.

### Buffering

Среда исполнения обязана буферизировать события и сигналы, поступающие вне активного `ЖДИ`. Лимит буфера является host-defined behavior. При превышении лимита среда исполнения порождает ошибку исполнения.

### Close

Поток закрывается с разрешением обещания `?name`. После закрытия `СИГНАЛ` в этот поток считается ошибкой исполнения.

### `~name` creation

Язык определяет операторы, которым разрешено открывать `~name` (`ВЫПОЛНИ`, `ДУМАЙ`, `НАПИШИ`). Хост-среда решает, будет ли поток реально создан для конкретного вызова — это зависит от capabilities провайдера.

### Типовой сценарий

```coil
ДУМАЙ решение
  ...
КОНЕЦ

НАПИШИ тех
  КУДА #быстрые_вопросы
  КОМУ @тех_отдел
  ЖДАТЬ ЛЮБОЙ
  <<
  Нужна возможная причина сбоя и временный обход.
  >>
КОНЕЦ

ЖДИ
  НА ?тех
КОНЕЦ

СИГНАЛ ~решение
  <<
  $тех
  >>
КОНЕЦ
```

## 7.8. Открытые вопросы (deferred)

Следующие области сознательно не нормализуются в текущем цикле:

| Область | Описание |
|---|---|
| **Broadcast vs compete** | Может ли несколько потребителей ждать событие из одного потока? |
| **Cross-instance routing** | Доступ к потоку из другого экземпляра протокола |
| **Rich event shape** | Точная структура объекта события |
| **Событийная форма `ЖДИ ... ИЗ ~...`** | Синтаксис ожидания событий из потока |
| **Cancellation / interruption** | Модель отмены и прерывания потока |

---

## 7.9. Что считается архитектурно принятым

- Открытые потоки нужны языку.
- Размышление LLM — это не только «запуск и финал», но и живой канал для новых данных.
- Интерактивные инструменты с двусторонней связью укладываются в общую потоковую модель.
