# Решения

Журнал принятых проектных решений по языку COIL.

## Как ведётся этот журнал

Каждое проектное решение получает сквозной номер `D-NNNN`.

| Статус | Значение |
|---|---|
| `принят` | Решение зафиксировано и отражено в spec без серьёзных незакрытых дыр. |
| `принят как направление` | Архитектурный выбор сделан, но точная форма ещё уточняется в spec. |
| `заменён D-NNNN` | Решение заменено указанным. |

Процесс:
1. Принять решение → присвоить следующий `D-NNNN`, записать мотивацию, статус `принят`.
2. Заменить решение → старому присвоить `заменён D-NNNN`, новому — свой `D-NNNN`.

> Открытые вопросы живут в GitHub Issues, а не в этом журнале.

## D-0049 — `Typ.Object` (`ОБЪЕКТ`) в РЕЗУЛЬТАТ

| | |
|---|---|
| **Статус** | принят |
| **Решено** | 2026-03-31 |
| **Влияет на** | `spec/05-structured-output.md`, `spec/10-terminology.md`, `spec/02-core.md`, `dialects/*/` |
| **Контекст** | Field access (`$name.a.b.c`) стабилен в грамматике выражений (§ 3.7) и реализован в рантайме. Инструменты (`ВЫПОЛНИ`) возвращают произвольные объекты, и цепочечный доступ к ним работает. Но `РЕЗУЛЬТАТ` не мог произвести такую структуру — типа `ОБЪЕКТ` не существовало, а §5.5 явно запрещал вложенные объекты. Это создавало искусственную асимметрию: один и тот же паттерн доступа работал для результатов инструментов, но не для результатов `ДУМАЙ`. |
| **Решение** | Введён `Typ.Object` / `ОБЪЕКТ` — тип поля РЕЗУЛЬТАТ, представляющий одну запись с именованными полями. Разрешена вложенность: `ОБЪЕКТ` внутри `ОБЪЕКТ` (произвольная глубина), `СПИСОК` внутри `ОБЪЕКТ`, `ОБЪЕКТ` внутри `СПИСОК`. Запрещены: `СПИСОК` внутри `СПИСОК` (нет ясного пользовательского смысла), рекурсивные ссылки, union-типы. |
| **Последствия** | Тест `if-field-access.coil` становится валидным. Диалекты дополнены маппингом `Typ.Object`. Глубина вложенности не ограничена спецификацией — это concern реализации и LLM capabilities. |

## D-0046 — COIL-H: round-trip только для stable subset

| | |
|---|---|
| **Статус** | принят |
| **Решено** | 2026-03-31 |
| **Влияет на** | `spec/11-coil-h.md` |
| **Контекст** | Спека § 11.2 утверждала: «Любой валидный COIL-C должен иметь табличное представление.» Это обещание покрывает experimental-конструкции, для которых round-trip не может быть гарантирован. D-012-07 требовал сузить обещания. |
| **Решение** | § 11.2 переформулируется. Два уровня: (1) **Stable subset (обязательный):** COIL-H обязан отображать все stable-конструкции с полным round-trip (таблица → COIL-C → таблица). ## D-0045 — `КАЖДЫЙ`: вложенный scope на каждую итерацию

| | |
|---|---|
| **Статус** | принят |
| **Решено** | 2026-03-31 |
| **Влияет на** | `spec/03-extended.md`, `spec/04-execution-model.md` |
| **Контекст** | Спека не описывала scoping внутри `КАЖДЫЙ`. Если тело содержит `ДУМАЙ`, создаётся обещание `?name` — непонятно, конфликтует ли оно между итерациями и видимо ли вне цикла. |
| **Решение** | Каждая итерация `КАЖДЫЙ` создаёт вложенный scope. Обещания и значения, созданные внутри итерации, живут до конца итерации и не видны в следующих итерациях и за пределами цикла. Переменная элемента (`$task`) перебиндится на каждой итерации. |
| **Последствия** | `spec/03-extended.md` § 3.4 дополняется правилом вложенного scope. Это решение влияет на семантический валидатор: ссылка на `?name` или `$name`, созданные внутри `КАЖДЫЙ`, за пределами цикла — ошибка подготовки. |

## D-0044 — `КАЖДЫЙ` наблюдаемо последовательный

| | |
|---|---|
| **Статус** | принят |
| **Решено** | 2026-03-31 |
| **Влияет на** | `spec/03-extended.md` |
| **Контекст** | Спека § 3.4 содержала: «Среда исполнения вправе исполнять итерации параллельно, если между ними нет зависимостей по данным.» Это создавало три проблемы: (1) отсутствие зависимостей неразрешимо статически; (2) скрытая параллельность нарушает принцип явного поведения COIL; (3) для не-программиста «каждый» — последовательно. |
| **Решение** | `КАЖДЫЙ` наблюдаемо последовательный. Итерации исполняются в порядке элементов источника. Среда исполнения не должна изменять наблюдаемый порядок. Runtime-оптимизации, не влияющие на наблюдаемое поведение, допустимы. Формулировка § 3.4 о допустимости параллелизма **убирается**. Явная параллельная итерация — deferred; если понадобится, будет отдельная конструкция или модификатор. |
| **Последствия** | `spec/03-extended.md` § 3.4 обновляется: семантика переписывается. Примеры, допускающие чтение `КАЖДЫЙ` как параллельного, корректируются. |

## D-0043 — `ПОЛУЧИ`: observable contract без привязки к UX

| | |
|---|---|
| **Статус** | принят |
| **Решено** | 2026-03-31 |
| **Влияет на** | `spec/02-core.md` |
| **Контекст** | `ПОЛУЧИ` имел stable surface, но observable contract не фиксировал: категории источников, completion semantics, роль таймаута и тела. |
| **Решение** | (1) **Категории источников** — иллюстративные, не исчерпывающие: injected (конфигурация, контекст запуска), prompted (запрос у пользователя), configured (внешнее хранилище). Хост-среда вправе реализовать любую комбинацию. Это пояснительный текст, не enum. (2) **Completion:** шаг завершён успешно, когда `$name` связано с non-null значением. Пустая строка — допустимое значение. Отказ хост-среды или таймаут — ошибка исполнения. (3) **Таймаут:** модификатор `НЕ БОЛЕЕ` — опциональный. Без таймаута `ПОЛУЧИ` блокирует до предоставления или отказа. (4) **Тело:** опционально. Если присутствует, хост-среда вправе использовать как подсказку пользователю. |
| **Последствия** | `spec/02-core.md` § 2.6 дополняется: модификатор `НЕ БОЛЕЕ`, completion contract, опциональность тела. Consistent с `ЖДИ` и `НАПИШИ`, где `НЕ БОЛЕЕ` уже есть. |

## D-0042 — Уточнение D-0028: `~name` создаётся хост-средой, а не языком

| | |
|---|---|
| **Статус** | принят |
| **Решено** | 2026-03-31 |
| **Влияет на** | `spec/02-core.md`, `spec/04-execution-model.md`, `spec/07-streams.md` |
| **Контекст** | D-0028 утверждал: «`ВЫПОЛНИ` всегда создаёт `?name` и `~name`». Это заставляло runtime создавать фиктивный поток для one-shot инструментов. На практике хост-среда знает, какие провайдеры поддерживают потоковое взаимодействие, а какие — нет. |
| **Решение** | Язык определяет операторы, которым **разрешено** иметь потоковую проекцию `~name` (`ВЫПОЛНИ`, `ДУМАЙ`, `НАПИШИ`). Хост-среда решает, будет ли `~name` реально создан, исходя из capabilities конкретного провайдера (модели, инструмента, участника). Обещание `?name` создаётся всегда (для операторов, которые его создают). `СИГНАЛ ~name` при неоткрытом потоке — ошибка исполнения. Уточняет D-0028. |
| **Последствия** | Формулировка в `spec/02-core.md` § 2.8 меняется: «`ВЫПОЛНИ` всегда создаёт `?name`; потоковая проекция `~name` создаётся, если хост-среда поддерживает потоковое взаимодействие для данного инструмента». Аналогично для `ДУМАЙ` и `НАПИШИ`. |

## D-0041 — End-of-stream: поток закрывается с разрешением обещания

| | |
|---|---|
| **Статус** | принят |
| **Решено** | 2026-03-31 |
| **Влияет на** | `spec/07-streams.md`, `spec/04-execution-model.md` |
| **Контекст** | При нормализации stream MVP нужен минимальный close contract без введения отдельного оператора закрытия потока. |
| **Решение** | Поток `~name` закрывается, когда обещание `?name` разрешено (успешно или с ошибкой). После закрытия `СИГНАЛ ~name` — ошибка исполнения. Отдельный оператор закрытия потока не вводится в v0.4. |
| **Последствия** | Жизненный цикл потока привязан к жизненному циклу обещания. Это простая ментальная модель: поток жив, пока работа не завершена. |

## D-0040 — `СИГНАЛ` асинхронный и кооперативный

| | |
|---|---|
| **Статус** | принят |
| **Решено** | 2026-03-31 |
| **Влияет на** | `spec/03-extended.md`, `spec/07-streams.md` |
| **Контекст** | Спека и D-0013 утверждали, что `СИГНАЛ` — кооперативный и не hard interrupt, но не фиксировали конкретную семантику. |
| **Решение** | `СИГНАЛ` помещает данные в буфер потока. Протокол продолжает исполнение, не дожидаясь обработки. Получатель (LLM, инструмент) принимает сигнал в своей согласованной точке (между шагами reasoning, между итерациями tool). Среда исполнения не прерывает текущую операцию получателя. Нет гарантии, что получатель обработал сигнал к моменту следующего шага протокола. |
| **Последствия** | `СИГНАЛ` — fire-and-forget с точки зрения протокола. Если автору нужна гарантия обработки, он ждёт события из потока после сигнала. |

## D-0039 — Stream MVP: ownership, ordering, buffering

| | |
|---|---|
| **Статус** | принят |
| **Решено** | 2026-03-31 |
| **Влияет на** | `spec/07-streams.md`, `spec/04-execution-model.md` |
| **Контекст** | Потоковая модель имела stable namespace `~name`, но ownership, ordering и buffering оставались deferred. Для реализации runtime нужен минимальный implementable contract. Рабочая гипотеза из § 7.7 проверена и признана достаточной для v0.4. |
| **Решение** | (1) **Ownership:** поток `~name` принадлежит экземпляру протокола, создавшему его. Только этот экземпляр может отправлять `СИГНАЛ` в `~name` и ждать событий из `~name`. Cross-instance stream access — deferred. (2) **Ordering:** FIFO в каждом направлении: события из потока доставляются в порядке порождения; сигналы в поток доставляются в порядке отправки. (3) **Buffering:** если событие пришло вне активного `ЖДИ`, среда исполнения обязана буферизировать его. Буферизированные события доставляются при следующем `ЖДИ` в порядке FIFO. Лимит буфера — host-defined; overflow — ошибка исполнения. |
| **Последствия** | Статусная карта § 7.1a обновляется: ownership, ordering, buffering переходят из deferred в stable (minimal contract). Broadcast, compete, cross-instance delivery остаются deferred. Rich event shape и событийная форма `ЖДИ ... ИЗ ~...` остаются experimental. |

## D-0038 — Согласованность структур сообщений — бизнес-задача

| | |
|---|---|
| **Статус** | принят |
| **Решено** | 2026-03-31 |
| **Влияет на** | `spec/04-execution-model.md`, `spec/09-os-integration.md` |
| **Контекст** | Если payload сообщения может быть структурированным объектом, возникает вопрос: кто валидирует совместимость структур между отправителем и получателем? |
| **Решение** | COIL не валидирует payload на входе и не проверяет совместимость структур между агентами. Согласованность структур (отправитель пишет объект, получатель умеет его читать) — ответственность бизнеса/приложения. Валидация payload на стороне получателя (аналог `РЕЗУЛЬТАТ` для входящих) — deferred. Типизация каналов — deferred. |
| **Последствия** | Язык остаётся простым; бизнес-логика не просачивается в языковую норму. |

## D-0037 — Модель сообщения: envelope + payload

| | |
|---|---|
| **Статус** | принят |
| **Решено** | 2026-03-31 |
| **Влияет на** | `spec/02-core.md`, `spec/04-execution-model.md`, `spec/09-os-integration.md` |
| **Контекст** | При фиксации result contract для `НАПИШИ` встал вопрос: что содержит результат (reply) и что может содержать само сообщение. COIL-сценарии порождают структурированный выход через `ДУМАЙ` + `РЕЗУЛЬТАТ`, и этот выход должно быть возможно передать другому агенту без потери структуры. |
| **Решение** | Сообщение двуслойное: **envelope** (обёртка, host-defined: кто ответил, когда, метаданные доставки) + **payload** (содержимое: текст или структурированный объект). Payload может быть текстом или объектом — определяется бизнесом. Конкретный shape envelope — host-defined behavior. Это позволяет цепочке `ДУМАЙ → НАПИШИ → другой агент` сохранять структуру сквозь. |
| **Последствия** | Хост-среда обязана поддерживать объектный payload. UI обязан уметь отображать объектные сообщения. Спека не ограничивает payload текстом. |

## D-0036 — Minimal result contract для `НАПИШИ` + `ЖДАТЬ`

| | |
|---|---|
| **Статус** | принят |
| **Решено** | 2026-03-31 |
| **Влияет на** | `spec/02-core.md`, `spec/04-execution-model.md` |
| **Контекст** | `НАПИШИ` имел stable lifecycle (три политики ожидания), но shape результата оставался experimental. Автор сценария не знал, что лежит в `$name` после ожидания. |
| **Решение** | (1) `ЖДАТЬ НЕТ` + имя результата — ошибка подготовки; fire-and-forget не создаёт обещание. (2) Если `ЖДАТЬ` опущен, подразумевается `ЖДАТЬ НЕТ`. (3) `ЖДАТЬ ЛЮБОЙ`: результат — один reply (envelope + payload); envelope host-defined, payload — текст или объект. (4) `ЖДАТЬ ВСЕ`: результат — коллекция replies в хронологическом порядке (порядок поступления). (5) Таймаут при `ЖДАТЬ ВСЕ` — ошибка исполнения; partial results — deferred. (6) Корреляция ответов с обещаниями — host-defined; среда обязана обеспечить корректную привязку. |
| **Последствия** | `spec/02-core.md` § 2.9 обновляется: правило «имя + ЖДАТЬ НЕТ = ошибка», default ЖДАТЬ. `spec/04-execution-model.md` § 4.7 обновляется: shape переходит из experimental в stable (minimal contract). Числовой доступ по индексу для коллекции — deferred; итерация через `КАЖДЫЙ`. |

## D-0035 — Неравенство через `НЕ`, оператор `!=` отсутствует

| | |
|---|---|
| **Статус** | принят |
| **Решено** | 2026-03-31 |
| **Влияет на** | `spec/03-extended.md`, `spec/10-terminology.md` |
| **Контекст** | При фиксации expression grammar встал вопрос об операторе неравенства. `!=` — единственный оператор, который объединяет два понятия (отрицание + равенство) в один символ, нарушая ортогональность набора. COIL уже имеет логическую связку `НЕ`. |
| **Решение** | Оператор `!=` не входит в язык. Неравенство выражается через `НЕ ($x = значение)`. Набор операторов сравнения: `=`, `<`, `>`, `<=`, `>=`. Логические связки: `И`, `ИЛИ`, `НЕ`. Каждый элемент делает ровно одно. |
| **Последствия** | Скобки после `НЕ` де-факто обязательны при отрицании сравнения. Многословность (`НЕ ($x = 5)` вместо `$x != 5`) — приемлемая цена за ортогональность и читаемость для не-программистов. |

## D-0034 — Одинарное `=` вместо `==` для равенства

| | |
|---|---|
| **Статус** | принят |
| **Решено** | 2026-03-31 |
| **Влияет на** | `spec/03-extended.md`, `spec/10-terminology.md` |
| **Контекст** | В COIL нет оператора присваивания `=` — присваивание выражается через `ОПРЕДЕЛИ` / `УСТАНОВИ` / `ПОЛУЧИ`. Классическая причина существования `==` (отличие от `=`) отсутствует. Для не-программиста `=` — это равенство (школьная математика), а `==` — необоснованный синтаксический налог. |
| **Решение** | Оператор равенства — `=` (одинарный). `==` не является частью языка. Символ `=` не используется нигде в COIL кроме выражений сравнения, парсерных конфликтов нет. |
| **Последствия** | Программисты могут рефлекторно читать `=` как присваивание, но контекст (только внутри `ЕСЛИ` и `ПОВТОРЯЙ ДО`) снимает неоднозначность. При конфликте приоритетов пользователь важнее программиста. |

## D-0033 — Minimal expression grammar для v0.4

| | |
|---|---|
| **Статус** | принят |
| **Решено** | 2026-03-31 |
| **Влияет на** | `spec/03-extended.md`, `spec/10-terminology.md`, `ROADMAP.md` |
| **Контекст** | `ЕСЛИ` и условный `ПОВТОРЯЙ` имели stable condition slot, но expression grammar оставался experimental. Это создавало разрыв: frozen surface с дыркой в семантике. Для v0.4 необходимо зафиксировать минимальный набор выражений, достаточный для реальных сценариев. |

## D-0029 — Диалектная модель: ни один диалект не привилегирован в реализации

| | |
|---|---|
| **Статус** | принят |
| **Решено** | 2026-03-24 |
| **Влияет на** | `spec/00-overview.md`, `spec/01-lexical.md`, `spec/10-terminology.md`, `dialects/*` |
| **Контекст** | COIL поддерживает диалекты — наборы ключевых слов на разных языках и в разных стилях. Ранее русская форма (COIL-C) считалась канонической, что де-факто создавало привилегированный диалект и зашивало русские ключевые слова в код реализации. |
| **Решение** | В коде реализации нет зашитых ключевых слов. Все маппинги «ключевая фраза → оператор/модификатор» загружаются из внешних диалектных таблиц. Ни один диалект не имеет привилегированного статуса в реализации. COIL-C (code) — текстовая форма языка на конкретном диалекте; буква «C» означает «code», а не «canonical» в смысле конкретного набора ключевых слов. Уточняет D-0018. |
| **Инварианты** | (1) Скрипт написан ровно на одном диалекте. (2) Сигилы (`$`, `?`, `@`, `!`, `#`, `~`) наддиалектны и не меняются. (3) Семантика оператора не зависит от диалекта. (4) AST не содержит ключевых слов — только абстрактные идентификаторы операторов и модификаторов. (5) Диагностика показывается в терминах диалекта скрипта. (6) Добавление нового диалекта не требует изменений в парсере, валидаторе или среде исполнения. (7) Ключевое слово в диалекте — это потенциально фраза из нескольких слов, а не одно слово. |
| **Последствия** | Лексер инициализируется диалектной таблицей и строит обратный индекс «фраза → абстрактный идентификатор». Парсер, валидатор и среда исполнения работают только с абстрактными идентификаторами. Диагностический слой имеет доступ к обратному маппингу для формирования сообщений на языке диалекта. Формат абстрактных идентификаторов и структура диалектных таблиц определяются отдельно. |
